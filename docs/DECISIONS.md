# HealthAI 重要技術決策

## ADR-001：客戶端使用 uni-app

決定：客戶端使用 uni-app Vue 3 TypeScript。

原因：需要同時預留 H5、Android、iOS 與微信小程序，並共用手機端頁面與業務流程。

## ADR-002：健管師需要手機端

決定：健管師使用另一組 uni-app 角色頁面，不只使用 Web。

原因：健管師需要隨時查看客戶、收到通知、處理新配對與即時回覆。

## ADR-003：Admin 使用獨立 Web

決定：Admin 使用 `console/` 獨立 Web 後台。

原因：Admin 需要大量表格、派單、監控、價格設定、內容管理與審計功能，桌面 Web 更適合。

## ADR-004：三端共用後端，但不共用角色畫面

決定：客戶端、健管師手機端、Admin 共用 API、資料模型與權限規則，但使用不同畫面與入口。

原因：三種角色的工作目標不同，混在同一組頁面會讓導航、權限與維護變複雜。

## ADR-005：Provider 介面隔離外部服務

決定：微信登入、支付、OCR、AI、推播、語音都透過 Provider 介面。

原因：第一階段需要 Mock，正式上線時可以更換服務商而不重寫產品流程。

## ADR-006：健康資料必須保留來源與審計

決定：報告解析、手動錄入、客戶修正與 AI 結果都要保存來源、版本與操作者。

原因：健康資料敏感且可能需要追溯，不能只保存最後一個數值。

## ADR-007：配對成功必須通知健管師與客戶

決定：派單、配對、新訊息與逾時都產生通知事件。

原因：健管師需要及時回覆客戶，單靠客戶主動刷新頁面不可靠。

## ADR-008：諮詢以房間為核心，不以預約卡片為核心

決定：客戶建立 ConsultationRequest，經公司派單後建立 Conversation；客戶與健管師在同一個諮詢房間內文字溝通，語音作為可選通道。

原因：產品真正的服務價值是配對後的持續溝通與健康資料解讀，而不是單純完成一次預約。

## ADR-009：文字通道必須獨立於語音通道

決定：文字訊息是諮詢房間的必要能力；語音 Provider 失敗、拒絕或尚未接入時，不能阻斷文字聊天。

原因：第一階段先確保客戶與健管師可以穩定溝通，正式語音服務可以後置替換。

## ADR-010：公司控制分配與排班，健管師控制在線狀態

決定：Admin 管理時段、容量、免費資格與派單；健管師手機端只管理在線/離線與處理分配的客戶。

原因：避免健管師自行調整客戶可預約時間，確保平台能統一監控服務量與回覆時效。
